Stablepay

The Carry-Forward Flow

Integration Guide  ·  v1  ·  2026

Overview

Every Stablepay payment follows a consistent 3-step flow: validate the account, get the rate, then submit the payment. Fields returned at each step must be passed forward exactly as-is into the next call — this ensures the name, operator code, and amounts are consistent end-to-end.

Why carry-forward matters The paymentCode from /validate is the authoritative operator or bank identifier as resolved by Stablepay. Always use this value — not what the user typed — when submitting a payment. Similarly, accountName must be echoed back exactly; providers use it for name-match verification.

Payout (Money Out) USDC → Fiat

Merchant sends USDC on-chain; recipient receives fiat via MOMO or bank transfer.

Step 1
Validate the recipient account
Resolve the account number to a registered name and detect the MNO operator (MOMO) or confirm the bank code (BANK). Call once per payment — not on each retry.
curl -X POST https://api.stablepay.app/v1/account/validate \
  -H "Authorization: Bearer <your-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "accountNumber": "+254712345678",
    "country":       "KE",
    "paymentMethod": "MOMO"
  }'

# Response:
# {
#   "accountName":   "Jane Doe",
#   "accountNumber": "+254712345678",
#   "paymentCode":   "MPESA",
#   "country":       "KE",
#   "currency":      "KES",
#   "paymentMethod": "MOMO"
# }
Carry forward → accountName accountNumber paymentCode country currency paymentMethod
↓
Step 2
Fetch the FX rate
Lock an exchange rate before submitting. Rates expire after 60 seconds — show the rate for user confirmation and submit immediately. Never cache rates across sessions.
curl -X GET "https://api.stablepay.app/v1/fx/rate?from=USDC&to=KES&blockchain=BSC" \
  -H "Authorization: Bearer <your-api-key>"

# Response:
# {
#   "rate":      "129.500000",
#   "fee":       "0.200000",
#   "expiresAt": "2026-07-01T12:01:00Z"
# }
Carry forward → rate fee
↓
Step 3
Submit the payout
Pass all fields from steps 1 and 2 directly. Use a stable Idempotency-Key to safely retry on network failures — the same key on a retry returns the original result without double-paying.
curl -X POST https://api.stablepay.app/v1/payments/moneyout \
  -H "Authorization: Bearer <your-api-key>" \
  -H "Idempotency-Key: <unique-uuid>" \
  -H "Content-Type: application/json" \
  -d '{
    "fiatAmount":    "1000",
    "currencyIn":    "USDC",
    "currencyOut":   "KES",
    "country":       "KE",
    "blockchain":    "BSC",
    "paymentMethod": "MOMO",
    "accountName":   "Jane Doe",
    "accountNumber": "+254712345678",
    "paymentCode":   "MPESA",
    "reference":     "order-001"
  }'

Collection (Money In) Fiat → USDC

Customer pays fiat via MOMO; merchant receives USDC in their treasury wallet. The full fiat amount is charged to the customer — the processor fee is deducted from the USDC received.

Step 1
Validate the customer account
Same as payout — resolve the phone number to a name and auto-detect the MNO. The paymentCode returned (e.g. MPESA) is passed to the collection endpoint.
curl -X POST https://api.stablepay.app/v1/account/validate \
  -H "Authorization: Bearer <your-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "accountNumber": "+254712345678",
    "country":       "KE",
    "paymentMethod": "MOMO"
  }'

# Response:
# {
#   "accountName":   "Jane Doe",
#   "accountNumber": "+254712345678",
#   "paymentCode":   "MPESA",
#   "paymentMethod": "MOMO"
# }
Carry forward → accountName accountNumber → phoneNumber ★ paymentCode
↓
Step 2
Convert the fiat amount
Get the USDC equivalent for the amount the customer will pay. convertedAmount is what the merchant actually receives after the processor fee is deducted.
curl -X POST https://api.stablepay.app/v1/payments/moneyin/convert \
  -H "Authorization: Bearer <your-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "fiatAmount":          "500",
    "sourceCurrency":      "KES",
    "destinationCurrency": "USDC",
    "blockchain":          "BSC"
  }'

# Response:
# {
#   "convertedAmount":          "3.841",  ← merchant receives this
#   "exchangeRate":             "130.18",
#   "processorFee":             "2",      ← deducted from USDC, not from customer
#   "senderFiatAmount":         "500",
#   "expectedUsdcFromProvider": "3.841"
# }
Carry forward → fiatAmount sourceCurrency destinationCurrency
↓
Step 3
Submit the collection
Initiates a MOMO prompt to the customer's phone. Note: accountNumber from /validate becomes phoneNumber here. All other fields keep the same name.
curl -X POST https://api.stablepay.app/v1/payments/moneyin \
  -H "Authorization: Bearer <your-api-key>" \
  -H "Idempotency-Key: <unique-uuid>" \
  -H "Content-Type: application/json" \
  -d '{
    "fiatAmount":          "500",
    "sourceCurrency":      "KES",
    "destinationCurrency": "USDC",
    "blockchain":          "BSC",
    "paymentMethod":       "MOMO",
    "phoneNumber":         "+254712345678",
    "accountName":         "Jane Doe",
    "paymentCode":         "MPESA",
    "reference":           "collection-001"
  }'

Tips & Common Mistakes

  • Always use paymentCode from /validate. Never substitute raw user input. The resolved code (e.g. MPESA) is what the provider expects and may differ from what the user typed.
  • Rates expire in 60 seconds. Fetch the rate, show it for confirmation, and submit immediately. Do not cache rates across sessions or reuse them on separate payment attempts.
  • Use stable Idempotency-Keys. Generate a UUID per payment attempt and reuse the same key on retries. This guarantees at-most-once execution even if the request times out.
  • Do not re-validate on retries. /validate should be called once per payment initiation. On network retries, reuse the values from the original validate response.
  • BANK payments require paymentCode at validate time. For BANK method, the bank code must be supplied in the validate request body and will be echoed back for carry-forward.
